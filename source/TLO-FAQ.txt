Q: Is TLO a commercial application?
A: No. TLO is freeware.

Q: What does TLO do well?
A: TLO inventories live-music collections, identifies show metadata, creates searchable inventory output, and can tag supported audio files. Results depend on folder names, setlists, tags, database coverage, and optional online lookup sources.

Q: Does TLO inventory absolutely every music file?
A: No. TLO inventories supported music/media file types under eligible inventory roots, but deliberately skips operating-system-managed folders and TLO-owned work/temporary trees. Within eligible roots, it continues checking nested folders after it finds music in a parent show folder so a nested opening act can be discovered as a separate show. Ordinary CD/Disc/Set wrapper folders continue through the normal grouping rules.

Q: Do I need to define TLOHome before I start?
A: Yes. TLOHome is the root for the applications, databases, logs, setlists, and inventory output. Set it with the TLOHome environment variable or the documented --TLOHome command-line option. The Inventory and Search GUIs resolve it at startup and display it as a read-only label.

Q: What else is required before the first run?
A: A complete installation must contain TLOHome/TLO_DBs/artists.sqlite and TLOHome/TLO_DBs/venues.txt. Full Inventory also requires Search Path. Path(s) can contain one or more semicolon-separated direct roots using the same line grammar as toBeInventoried.txt, or the fully qualified path to any .txt control file using that format. TLOHome/toBeInventoried.txt is not read automatically. Optional settings include TLOCurrentStorage for Add Shows, SETLISTFM_API_KEY for setlist.fm lookup, and SETLISTFMUPGRADE_API_KEY (or SETLISTFM_UPGRADE_API_KEY) to enable setlist.fm upgrade. The upgrade variable should contain the same API key value as SETLISTFM_API_KEY. Explicit nonblank process/session values take precedence. On Windows, TLO checks current persisted User/System environment values only as fallback when the corresponding process value is missing or blank because the launching parent has a stale environment snapshot.

Q: Is toBeInventoried.txt still used automatically?
A: No. TLO keeps toBeInventoried.txt only as an example/template in COMPLETE installations. To use that format, explicitly put the full path to toBeInventoried.txt (or any other .txt control file) in Path(s).

Q: Can Search Path contain more than one root?
A: Yes. Separate direct Path(s) entries with semicolons. Each direct entry may use the same optional [Volume], --/slam, --/copy, and --/copy-delete directives as a control-file line. A .txt Search Path entry is expanded using the same line/comment rules as the former toBeInventoried.txt input file.

Q: Can I drag more than one folder into the Path(s) box?
A: Yes, on native Windows. The Windows TkDND handling ensures that every folder or .txt control file selected in one drag is retained, and each later drag appends to the existing Path(s) value instead of replacing it. Items are separated automatically with semicolons. For example, dragging A, then B, then C and D together produces A;B;C;D. Commas are ordinary path characters, so a dropped folder such as Van Morrison 1994-12-03 Dublin, Ireland needs no special quoting.

Q: Can two Inventory runs use the same TLOHome at the same time?
A: No. TLO enforces one inventory-mutating run per TLOHome with a cross-process lock held for the duration of the run. A second Full Inventory is rejected before tokenized logs or inventory output are changed. Search and unrelated read-only operations may still use that TLOHome. If the first process crashes, the operating system releases the lock automatically so a later Inventory can proceed.

Q: How difficult is it to set the TLO-related environment variables?
A: The Windows and macOS/Linux/WSL setup steps are described in Sections 4 through 7 of the User Manual.

Q: Can TLO change or remove original material?
A: Yes. By default, Full Inventory and standalone tlo-tag move proven-corrupt FLAC/MP3 files to the operating-system Trash/Recycle Bin; Full Inventory also moves a folder when 100% of its audio files are corrupt. For an actual run, if you do not want TLO to move any corrupt files or folders to the Trash/Recycle Bin, select Keep and report in the GUI or use --corrupt-files keep in standalone tlo-tag. Dry Run never moves or deletes files or folders, regardless of the selected corruption policy. Rename Compliantly, Tag in Place, SHN-to-FLAC conversion, and Tag Copy/Delete Original can also change or remove originals when selected. Same-partition Copy/Delete Original transfers are directory moves. Ordinary Tag Copy verifies the recursive relative file and folder structure and file sizes, without SHA-256 content comparison. Cross-partition Copy/Delete Original additionally verifies SHA-256 contents for every corresponding file before removing the original; same-partition Copy/Delete Original is a folder move. SHN conversion is verified before removing the source. The standalone tlo-reverse CLI can reverse logged Rename Compliantly, Tag Copy/Delete Original, and Tag Copy folder operations; audio tags are never restored or changed. Ambiguous or conflicting folder states are left untouched. Keep an independent backup when preserving pristine source material matters.

Q: What happens to an Add Shows cleanup entry when a POSIX/WSL volume has no label?
A: TLO fails closed. deleteBackupFolders.sh does not contain an active rm -rf for that unlabeled entry. It prints a SKIPPED/manual-verification message and leaves the example delete command commented out. Verify the intended volume and path yourself before enabling that command. Windows deleteReplacedFolders.bat records its guarded Windows cleanup behavior separately.

Q: What should I do if Inventory says an interrupted sibling-collection move requires recovery?
A: TLO normally recovers the journaled move automatically before scanning and then continues Inventory. This includes the case where the recovery container has the same pathname as one of the original collection members and the case where the journal was written with native-Windows paths (for example E:\boots\...) but recovery is running under WSL (/mnt/e/boots/...), or vice versa. TLO translates those equivalent path forms before applying the same strict parent/member validation. If automatic recovery cannot proceed, TLO prints the recovery container, journal, planned final folder, every original/staged member path with its current state, and the original journal path form when it differs. Close programs that may have those folders open and run a normal (non-Dry-Run) Inventory again. Do not delete the .tlo-sibling-consolidation.json journal or manually merge/delete the recovery folder; BOTH or MISSING states require review of the exact paths TLO reports. Dry Run never moves folders and will tell you to run a normal Inventory for recovery.

Q: What happens when an alternate collection already has an unsuffixed folder with the same name as the collection?
A: TLO does not create a nested Name\Name folder. TLO builds the aggregate in a new temporary sibling directory, moves the unsuffixed original member into it as Name (alt0), then moves alt1, alt2, and later accepted alternatives alongside it before finalizing the aggregate under the normal shared collection name. alt0 remains first for continuous collection-wide track numbering. If the transaction fails or is interrupted, the journal records both the original and staged names so rollback restores the exact original unsuffixed folder. Older compatible recovery journals remain supported.

Q: What happens if I inventory the same drive again?
A: For a named volume, TLO deterministically replaces, prunes, or appends the affected scope according to whether the new path is the same as, a parent of, a child of, or separate from the stored paths. It does not ask a Skip/Re-inventory question. Blank-volume runs append to the shared blank-volume logs and can create duplicate inventory entries if the same content is scanned again.

Q: Can Rename Compliantly rename my entire collection or search root?
A: No. TLO may aggregate true CD, disc, part, or volume siblings only when every direct music-bearing child under the parent belongs to that one release relationship. If any direct music-bearing sibling is unrelated, the folders remain separate and the broad collection/search parent is never renamed as one show. Text such as v.2 inside a larger descriptive parenthetical does not count as a volume suffix.

Q: Does Artist in Album Tag apply during Full Inventory?
A: Yes. When checked, Full Inventory and GUI Tag with Tag in Place, Tag Copy, or Tag Copy/Delete Original write Album as Artist followed by the resolved date, venue, location, and preserved parentheticals. Add Shows tagging and standalone tlo-tag use the same album rule.

Q: Can I see what TLO plans to do before it changes anything?
A: Yes. Full Inventory, Add Shows, and Tag show Review Operation before starting. Every Review Operation dialog reports all main-window checkbox values in the same order. Tag has no duplicated option checkboxes. GUI Tag now runs directly from the main Inventory window using the master Path(s), including any inline --/slam directives, the tag-mode choice, and all current main-window options; it no longer opens a separate Tag window. Add Shows retains only its action-specific controls. Dry run is controlled only by the checkbox on the main Inventory window. With Dry run selected, click Inventory, Tag, Process New Shows, or Process Potential Duplicate/Upgrades. Dry run resolves and displays resulting show names and planned actions. When tagging applies, it lists each applicable audio file with the Artist, Album, Track, and Title values that would be written, plus the title source, planned SHN-to-FLAC target, potential duplicate matches, or reason a file would be skipped. Dry run does not write tags, convert, rename, copy, move, delete, create inventory output, or change TLO logs.

Q: Are trailing folder parentheticals preserved in the resulting show name?
A: Yes. TLO captures trailing parenthetical items before it cleans the folder name for metadata parsing, then restores them after artist, date, venue, and location normalization. For example, Danny Gatton 1994-03-13 Bottom Line NYC (set 2) resolves to Danny Gatton 1994-03-13 Bottom Line New York, NY (set 2). Multiple trailing parentheticals remain in source order without duplicate entries.

Q: How does Check for updates choose a package if a release has only updates or only complete installs?
A: TLO first compares the latest GitHub release build number with the installed build. If that release is older than or equal to what is installed, TLO reports that no newer release is available and does not require signed metadata from the historical release. For a genuinely newer release, TLO requires independently signed TLO_UPDATE_METADATA.json and TLO_UPDATE_METADATA.sig before trusting the package. It then uses only the exact package for the installed operating system and package layout, preferring that platform/layout's update ZIP and falling back only to the exact matching complete ZIP. It never substitutes the source bundle, a generic ZIP, another operating system, or the other Windows onefile/onedir layout. TLO also rejects unsafe ZIP member paths, symbolic-link members, and excessive member count/decompression before validating the package manifest.

Q: What does Auto update do when it finds a newer build?
A: Auto update now asks before downloading. The prompt has Yes and Skip buttons. Yes downloads the verified exact-match ZIP to your Downloads folder and returns; TLO does not install or extract it. Skip closes the prompt and downloads nothing. The automatic check is still limited to at most once per day, so Skip does not cause another prompt on every startup during that interval. Manual Check for updates keeps its direct-download behavior.

Q: Can an update ZIP include the TLO databases?
A: Yes, when the release was explicitly built as a database-refresh update. Normal update ZIPs still omit TLO_DBs. A database-refresh update contains exactly TLO_DBs/artists.sqlite and TLO_DBs/venues.txt and omits your inventory, setlists, logs, staged folders, and other user-created output. Check for updates reads the package manifest and ZIP contents and tells you whether the downloaded update includes those databases; applying such an update replaces those two master database files.

Q: Does TLO recognize same-month multi-day dates such as 1970-04-12-13?
A: Yes. TLO accepts a first yyyy-mm-dd followed by one or two strictly ascending day values, using dashes or commas, for example 1970-04-12-13, 1970-04-12-13-14, 1970-04-12,13, and 1970-04-12,13,14. Textual equivalents such as 12-13 April 1970, April 12-13, 1970, and 1970 April 12-13 are also accepted. Every day must be valid for that month and year. The first day becomes the canonical TLO Date, while the complete original multi-day range is retained in PARENTHETICALS. A descending, repeated, or impossible range is rejected as a whole. Existing year-range rules are unchanged.

Q: Can TLO handle a folder such as RTF Paris 7 March 76 flac16?
A: Yes, but only through a guarded non-compliant fallback. The artist prefix itself must resolve uniquely in artists.sqlite; TLO does not manufacture initials, so RTF must already be an alias/artist term in the database. The date uses the normal TLO date parser, and everything after the date must be recognized technical media/source text such as flac16, flac24, shn, wav, 16-bit, 24-bit, SBD, AUD, FM, matrix, soundboard, or audience. Strong state/country-anchored place text and exact venues.txt matches are used normally. A single unanchored word such as Paris is only retained if eTreeDB, selected setlist metadata, and setlist.fm do not provide stronger venue/location information. Unknown multi-word text is not promoted to a location.

Q: Can Compliant and Rename Compliantly be selected together?
A: No. They are mutually exclusive. In the main Inventory window, checking either one automatically unchecks the other. Tag and Add Shows inherit the resulting main-window values. On the inventory, GUI-launcher, and standalone-tagger command lines, using --compliant and --rename-compliantly together produces an argument error.

Q: When does TLO ask for a Tag Copy destination?
A: Checking Tag Copy or Tag Copy/Delete Original only selects the mode. TLO asks for the destination after Inventory or the main-window Tag action is started, including when Dry run is selected. Both dialogs validate the full path and show available storage. Tag Copy copies the complete identified folder tree and verifies relative file paths, sizes, and descendant folder structure while retaining the source. The copy/delete dialog additionally warns that originals will be removed; same-partition transfers move the complete folder tree with no size totaling or comparison, while cross-partition transfers compare recursive relative file paths, descendant folders, and file sizes, then SHA-256 contents of every file, before deleting the original.

Q: How do I reverse a combined Tag Copy/Delete Original and Rename Compliantly run?
A: Run tlo-reverse with one fully qualified folder or containing path, for example tlo-reverse "D:\Music\moved show". TLO reads successful folder mappings from TLOHome/logs/tags*.txt and compatible tag*.log files and infers whether the logged action was Rename Compliantly, Tag Copy, or Tag Copy/Delete Original. No operation-type flag is normally required. Copy/Delete restores the exact logged destination to the exact original path, whether or not compliant renaming was enabled. Rename-only renames the folder back. Tag Copy leaves the original and removes only the exact logged copy after a file-set safety check. TLO also leaves the copy untouched when a destination file has a post-run modification timestamp indicating a possible later replacement; cross-filesystem restoration preserves symbolic links as links and verifies them before removing the logged destination. If more than one run is applicable, use a narrower path or --log; use --dry-run to preview. Audio tags are never changed. Results are appended to TLOHome/logs/reverseFolders.log.

Q: When does TLO call a same-named show a copy instead of an alternate?
A: A matching Show or compliant folder name is not enough. Before TLO uses a (copyN) qualifier or folder suffix, it compares the complete recursive trees. The relative folders (including empty folders), relative files, file sizes, and every file's byte contents must all match. TLO uses SHA-256 content comparison after the faster structure and size checks. If anything differs, or a comparison cannot be completed, TLO uses (altN) instead. File timestamps do not matter. A source folder that already carries (copyN) is also rechecked before that qualifier is used in the Show name.

Q: Where are the settings for each run recorded?
A: After you choose Start in Review Operation, TLO appends the action, local date/time, and the same reviewed settings lines to TLOHome/logs/runSettings.log. The file is shared by Full Inventory, Tag, Process New Shows, and Process Potential Duplicate/Upgrades, including Dry runs. Command-line Inventory and Tag use the same log. Choosing Go Back or closing Review Operation does not create an entry.

Q: Where do I find problems after a run?
A: The completion summary includes View Issues and Open Logs. View Issues groups consequential problems by reason, such as unidentified shows, missing setlists, track-title mismatches, unreadable audio, copy or verification problems, online lookup problems, and other tagging or file errors. Successful parser decisions such as selecting the correct contiguous numbered song block are informational and no longer appear as tagging warnings. Normal creation/update status for unidentifiedShows.txt, including a result of zero unidentified shows, is also informational and does not appear as a warning. The Issues window horizontal scrollbar now scrolls long Explanation and Path columns. Select an issue and use Open Path when TLO has a usable path for it.

Q: How can I donate to TLO?
A: Open the upper-right hamburger menu in the Inventory window and choose Donate. Donate > Venmo shows @James-Scarano-3. Donate > Check shows James Scarano, 49 Majestic Ave., Nashua, NH 03063. The donation details use normal dark menu text rather than disabled gray text.

Q: Why does the Current Operation activity indicator move slowly?
A: The indeterminate activity indicator moves at one-tenth of its former speed in Inventory, Tag, and Add Shows. This is only a visual animation change; it does not slow inventory, tagging, Add Shows, elapsed-time updates, or worker processing.

Q: Where does TLO store setlist.fm rate-limit information?
A: TLO stores it under TLOHome/logs/setlistfm-state. TLO no longer uses a shared system temporary-directory state file. A worker abandons a blocked reservation after 20 seconds and continues without that lookup.

Q: How do I safely remove duplicate folders?
A: Use tlo-deleteDupes with a fully qualified search path. TLO discovers candidate siblings from exact X/(copyN) families and from matching normalized artist/date names, then compares copies with one another as well as with unsuffixed folders. Folders with the same complete recursive structure, relative file names, and file sizes form a content-equivalence cluster. TLO keeps one folder per identical cluster, preferring an unsuffixed name; if the cluster contains only numbered copies, it keeps the lowest-numbered copy. The other identical cluster members are moved as whole folders into a folder named duplicates at the root of the partition containing the search path. Thus, if X differs from X (copy2) and X (copy3), but copy2 and copy3 match each other, TLO keeps X and copy2 and moves copy3. TLO creates the duplicates folder if needed, never overwrites an existing holding-folder entry, and appends each moved folder's original full path to TLOHome/deletedDirs.txt. When candidate folders differ, TLO records short CSV lines in TLOHome/deleteDupesMismatches.txt using folder name, folder name, and a simple reason such as different number of files, different sub-structure, or 01.flac different sizes.

Q: How can I research what TLO found in the comp and meta logs?
A: In the main Inventory window, click Research and enter an artist followed by a date, a venue, or a date. Research accepts every date form recognized by TLO Inventory, including partial/unknown forms such as xxxx-xx-xx, 19xx-xx-xx, 20xx-xx-xx, and 202x-xx-xx, textual-month dates, compact dates, slash dates, supported year ranges, and same-month multi-day ranges such as 1970-04-12-13 or 12-13 April 1970; a standalone four-digit 19xx/20xx year is also accepted. Multi-day ranges match using their canonical first day. TLO normalizes the date for matching and returns every matching metadata record plus all correlated comp-log paths. It then continues through every meta*.log and comp*.log line and adds an ALL RELATED RAW LOG LINES section with every directly related occurrence and its log filename/line number; it does not stop at the first occurrence. The standalone tlo-research app performs the same search and writes the same complete result to the console.

Q: Does TLO accept 19xx-xx-xx and 20xx-xx-xx as dates?
A: Yes. They are legitimate century-known partial dates. TLO requires the less-significant components to remain unknown, so 19xx-xx-xx and 20xx-xx-xx are valid, while forms such as 19xx-05-xx, 20xx-xx-14, 1xxx-xx-xx, and 2xxx-xx-xx are not.

Q: What does (pdupNN) mean in Add Shows?
A: When Process New Shows has Check for Duplicates selected and every matching bootlist entry is on another storage partition, TLO assumes those existing folders are unavailable for comparison and keeps the incoming show with a potential-duplicate marker such as (pdup01), (pdup02), and so on. This is not a copy/alternate determination. If a matching entry is on the current partition, or TLO cannot determine the partition, the existing duplicate review and copy/alternate checks remain in effect. Rename Compliantly applies the pdup marker to the physical folder name; otherwise the folder name is left as supplied.

Q: Does standalone tlo-tag use the same setlist.fm, Thorough Setlist Matching, and corruption controls as Inventory?
A: Yes. tlo-tag.py/tlo-tag.exe accepts the same lookup, Thorough Setlist Matching, corruption, and Delete Extra Tags controls. A standalone tlo-tag run now requires an explicit search folder (positional SEARCH_FOLDER or --search-folder; --tag-path remains a compatibility alias). Its corrupt-file policy defaults to delete, while its corrupt-folder policy defaults to never/keep unless you explicitly choose all or threshold; Full Inventory defaults to deleting proven-corrupt files and removing only 100%-corrupt folders. setlist.fm still requires eTreeDB. GUI Tag uses the current main-window values directly and no longer opens a separate Tag window. Corruption is checked before tag mutation using the same fail-closed rules as Inventory. When a real tagging mode is active, that pre-mutation check also performs a reversible temporary tag write/readback/restore/readback probe. Deep Audio Check is a separate default-off control (and --deep-audio-check CLI option) that decodes audio with TLO's bundled ffmpeg. For FLAC, a nonzero STREAMINFO total sample count must also match the actual decoded PCM samples, catching truncation even when ffmpeg reports success. If the expected count is missing or a reliable measurement cannot be obtained, the file is unverifiable, not automatically corrupt. Other formats may lack an authoritative duration; a clean decoder exit cannot always prove original completeness. A real decode failure is corruption; decoder unavailability, timeout, cancellation, access/I/O/resource, or validator-infrastructure failures are unverifiable and fail closed. When Deep Audio Check is off, non-tagging inventory checks only the header/metadata, not the complete audio stream. With real tagging, TLO also tests whether tags can be written and precisely restored. A header or metadata failure is classified as corrupt; a readable header does not prove the complete recording decodes. Dry Run never writes the probe tag or moves/deletes corrupt files or folders, regardless of the selected Corruption Handling policies. Dry Run may perform the read-only deep decode when enabled.

Q: Can TLO tag MP3 files and handle corrupt MP3 files like FLAC?
A: Yes. TLO treats MP3 as a first-class taggable format. MP3 files use the same Artist, Album, Track Number, and Title assignment flow as FLAC and participate in the same corruption population, percentage calculation, individual-file Keep/Delete policy, and folder Never/100%/threshold policy. Unverifiable MP3 reads fail closed just like FLAC.

Q: What does Delete Extra Tags do?
A: Delete Extra Tags is a main-window checkbox that defaults off and is also available as --delete-extra-tags. When selected, TLO clears tag metadata on files it tags and keeps only Artist, Album, Track Number, and Track Title. If the last active tagging mode is unchecked, Delete Extra Tags is also automatically unchecked and greyed out. Other metadata, including comments and embedded tag artwork where supported, is removed. When the checkbox is off, TLO preserves unrelated metadata under the established tagging rules.

Q: Does Tag still open a separate Tag window?
A: No. GUI Tag runs directly from the main Inventory window. Click Tag there; TLO uses the master Path(s), including inline --/slam directives, the selected tag mode, lookup/corruption/tagging options, Dry run, Performance Mode, and Max Workers ceiling. Progress and console output remain in the main window. The obsolete legacy TaggerWindow implementation is not shipped. The standalone tlo-tag command-line application remains available.

Q: What happens to the corruption folder controls when Corrupt files is Keep and report?
A: TLO treats Keep and report as report-only corruption handling. Folder removal is effectively Never, and the Folder removal and Folder corruption threshold controls are greyed out. Select Delete corrupt files to re-enable folder-removal choices; the threshold value is enabled only for At threshold.

Q: Why are the setlist.fm checkboxes disabled?
A: If SETLISTFM_API_KEY is missing or blank when the Main GUI starts, both setlist.fm controls are unchecked and disabled. If SETLISTFM_API_KEY is present but both SETLISTFMUPGRADE_API_KEY and SETLISTFM_UPGRADE_API_KEY are missing or blank, or if the accepted upgrade value does not exactly match SETLISTFM_API_KEY, normal setlist.fm remains available but setlist.fm upgrade is unchecked and greyed out. The GUI states whether the normal key is missing, the upgrade key is missing, or the values do not match, but never displays either key. Explicit nonblank CMD/PowerShell/process values take precedence. On Windows, persisted User/System values (including values added through Environment Variables or setx) are used only as fallback when the corresponding process value is missing or blank because the launching parent has a stale environment snapshot.

Q: What does Max Workers mean?
A: Max Workers is a ceiling, not a request to create that many workers. Unless a positive launcher value is supplied, the Main GUI sets it to the automatic maximum for the selected Performance Mode: gentle = 1, balanced = up to 2, fast = up to the CPU count, and extreme = up to four times the CPU count with a hard automatic ceiling of 64. Selecting a different Performance Mode resets Max Workers to that mode's automatic ceiling; you can then enter another positive ceiling. TLO may still use fewer workers because paths share a physical drive, there are fewer parallel work groups, or a phase must serialize work for correctness. Priority transitions are reversible: on Windows Fast/Extreme restore the startup process priority after Gentle/Balanced, while Linux/WSL/macOS keep the long-lived GUI/CLI parent at normal niceness and lower only spawned Gentle/Balanced workers.

Q: Will Rename Compliantly fix capitalization-only differences in a folder name?
A: Yes. TLO treats exact spelling and capitalization as part of the compliant folder name. If TLO resolves the canonical artist as Dave Van Ronk, a folder named dave van ronk 1978-02-17 Main Point Bryn Mawr, PA is renamed to Dave Van Ronk 1978-02-17 Main Point Bryn Mawr, PA. On case-insensitive filesystems TLO uses a temporary sibling rename when necessary so the exact capitalization is applied without treating the same folder as a collision or creating an alternate/copy suffix. TLO limits that capitalization correction to case-poor local text (for example kirjurinluoto / pori -> Kirjurinluoto / Pori) when the online value provides useful mixed case. Already good mixed-case text is not degraded to all caps, and a genuinely different online venue/location still does not override earlier path metadata. The rule applies to Full Inventory/GUI or standalone Tag and Add Shows.

Q: What does TLO do when a show or collection has xxxx-xx-xx and no venue or location?
A: TLO can add a separate non-geographic descriptor instead of inventing a venue or location. It looks conservatively at the setlist header before the track list for explicit Collection, Release, Session, Broadcast, Program, Recording, and similar labels; strong session/broadcast/collection text; quoted or decorated release titles; then a descriptive setlist filename; and finally meaningful folder-name residue after removing artist/date, disc/set/part, and technical-format tokens. Song rows, source/lineage text, generic housekeeping names, and prose are rejected. For example, a collection may become Pink Floyd xxxx-xx-xx Early Flights. The metadata log records DESCRIPTOR and DESCRIPTOR_SOURCE, while Venue and Location remain blank. If no safe descriptor is found, TLO keeps the normal Artist xxxx-xx-xx name.

Q: What syntax does the main Path(s) box use now?
A: The Path(s) box uses the same grammar as one toBeInventoried.txt data line, with multiple Path(s) entries separated by semicolons. A direct entry can be a path by itself or include [Volume], --/slam, --/copy, or --/copy-delete. Commas and apostrophes/single quotes are ordinary path/directive characters and do not require quotes. Matching double quotes remain accepted as optional explicit quoting. TLO automatically double-quotes a dragged path only when the folder name itself contains a literal semicolon, so that legal semicolon remains inside one Path(s) entry. Examples: C:\Boots\Grateful Dead ; C:\Boots\Pink Floyd --/slam Pink Floyd ; C:\Boots\Van Morrison 1994-12-03 Dublin, Ireland;D:\Incoming --/copy E:\TLOCopies. You can also enter the full path to any .txt control file that uses the normal toBeInventoried.txt line/comment rules.

Q: Where did the main Slam box go?
A: TLO does not use the separate Slam (optional) GUI field. Put an artist override beside the applicable Path(s) entry instead, for example C:\Incoming\RTF Paris --/slam Return to Forever. The inventory CLI --/slam option remains available for command-line use.

Q: What does Manual Tweaks do?
A: Manual Tweaks opens Manual Updates for user-directed folder/inventory corrections. Original accepts one folder or one .txt file. For a folder, enter the desired leaf folder name in New Name or drop one folder onto New Name; TLO keeps only its leaf name, and the drop does not depend on Original already containing a valid folder. Update Tags is checked by default. When it is checked, Save updates the tags in the corrected folder before finalizing the replacement setlist/bootlist inventory identity; uncheck it when you want the manual inventory correction without changing tags. TLO renames in place when needed, removes the old bootlist/setlist identity, and adds the new identity while preserving the old bootlist parent/volume path. If the folder was already renamed to the requested name in that same parent, Save can still repair the inventory. For a .txt Original, New Name is disabled and every non-comment line must be Path ----> Folder Name; blank lines, # comments, and REM comments are ignored. The one Update Tags choice applies to every line in that Save.

Q: What is Add New Shows?
A: Add New Shows is the incremental Add Shows/Updater workflow. It adds new content to the existing inventory without requiring a full rebuild; its two-line button label does not indicate a separate inventory engine.


Q: What happens in Manual Updates if Original is not in bootlist.csv but is still in unidentifiedShows.txt?
A: TLO checks unidentifiedShows.txt by exact Original path first and then by a unique matching leaf folder name. If it finds the unresolved show, it opens "Where is the unidentified show going?" and asks only for the destination Path. TLO does not move or rename anything in this branch; the physical change is assumed to have already been done manually. Enter or drop either the destination parent folder or the already-renamed New Name folder itself. If the supplied Path already ends in New Name, TLO strips that leaf to get the parent; otherwise it uses the supplied Path as the parent. If Update Tags is checked (the default), TLO updates the tags in that already manually changed folder before finalizing the inventory update; if unchecked, it leaves its tags alone. A parseable New Name is authoritative for the corrected Artist/Album tag identity, and SHN conversion is disabled inside Manual Updates so SHN originals are not removed by this repair workflow. TLO then inventories parent\New Name, removes the resolved line from unidentifiedShows.txt, writes canonical [Volume] rootless-path inventory data, and exports the replacement setlist. A .txt Manual Updates batch uses the same rule and collects all required destination prompts before applying the batch.

Q: Do commas or apostrophes in Path(s) require quotes?
A: No. Semicolons are the Path(s) entry separator. Commas and apostrophes/single quotes are ordinary characters inside paths and directive values. TLO accepts names such as Tito Puente's without treating the apostrophe as the start of a quoted value or reporting an unmatched quote. Matching double quotes remain accepted as optional explicit quoting. TLO automatically double-quotes a dragged path only when the folder name itself contains a literal semicolon, so that legal semicolon remains inside one Path(s) entry.

Q: Can MP3 tags help identify a show during Inventory?
A: Yes, in non-compliant mode. TLO samples metadata from up to two supported FLAC or MP3 files and can use ALBUMARTIST, ARTIST, ALBUM, and DATE as low-priority identification evidence. Artist evidence still follows the normal precedence: inline --/slam and stronger path/setlist evidence come first; a DB-matched sampled tag artist is used only after those stronger sources fail, and an unmatched raw tag artist is the final fallback. Compliant mode does not read or use FLAC or MP3 metadata tags.

Q: Does tlo-main accept --tag-path?
A: No. The GUI launcher uses the required main Path(s) field, including inline --/slam directives, and does not accept --tag-path. Standalone tlo-tag requires its own explicit search folder. Use positional SEARCH_FOLDER or --search-folder; --tag-path remains a compatibility alias for standalone tlo-tag only.

Q: When can setlist.fm run if eTreeDB already found the show?
A: In normal mode, setlist.fm remains a fallback when eTreeDB did not return usable venue/location data. Thorough Setlist Matching is the explicit exception: when Thorough and setlist.fm are enabled, TLO may query setlist.fm proactively for corroboration/deconfliction even after eTreeDB returned usable data. Thorough collection does not give setlist.fm extra overwrite authority.

Q: How does TLO treat untrusted collection metadata and recovery state?
A: TLO treats collection metadata and recovery state as untrusted input. TLO encodes control characters before writing machine-parsed logs, rejects malformed duplicate identity keys, bounds full setlist reads, refuses symlinked Tag Copy trees and symlinked sibling setlists, secures SHN temporary output, protects bootlist.csv from spreadsheet-formula interpretation, and prevents Issues actions from opening network/device paths or launching arbitrary files. Normal well-formed collections continue to use the same inventory/tagging behavior.

Q: Why can an interrupted sibling-collection recovery now stop instead of recovering automatically?
A: Automatic recovery now requires the recovery journal to match a nonce registry entry written by the same TLOHome under TLOHome/logs/sibling-recovery. This prevents a traded collection from planting a fake journal that tells TLO to move or delete unrelated files. A journal that is missing, oversized, malformed, or not registered stops Inventory without mutating the recovery container. Preserve the reported recovery container and journal for review rather than deleting them manually.

Q: Why can Tag Copy refuse a folder containing symbolic links?
A: TLO refuses Tag Copy when the source tree contains symbolic links so TLO cannot accidentally copy the contents of a link target outside the traded collection. Sibling setlist aggregation likewise ignores symlinked setlist files. Replace or remove the links deliberately before using those workflows.

Q: What does Copy Requests do?
A: Open the upper-right hamburger menu in the Inventory window and choose Copy Requests. Copy Requests copies a requested subset of the inventory to a Destination across multiple sessions and changing sets of connected source drives. A request stays saved under TLOHome/copyRequests, so you can copy what is available now, swap drives later, choose Continue, and TLO skips Shows already completed for that request. Active passes are transactionally recorded and locked so an interrupted pass can safely recover its own reservation/temp on the next Continue. Cancel Copy stops between files, cleans the current TLO-owned pending transaction, preserves completed items, and leaves the request Open.

Q: What can I put in Copy Request Path(s)?
A: Path(s) follows the same semicolon and optional-double-quote rules as the main Inventory Path(s) field. You may mix plain request text, rooted filesystem paths/volume items, and .txt request files in one field, for example c:\tmpBoots; c:\tlo\copyMe.txt; Allman Brothers Band. Repeated native-Windows drag/drop appends entries rather than replacing the field. A .txt entry is expanded immediately and uses the same blank-line, #, and REM whole-line comment convention as toBeInventoried.txt; TLO persists the usable lines in the saved Copy Request, so that source .txt file does not need to remain available for Continue. A rooted path ending in * is also expanded immediately: c:\TLO* selects each immediate folder in c:\ whose name begins with TLO, while c:\TLO\* selects the immediate folders inside c:\TLO without copying c:\TLO itself. Only folders are wildcard matches; files and symbolic-link folders are ignored. Wildcards inside .txt request files use the same rule. The wildcard parent must be accessible and at least one folder must match when the request is first created; the resolved folder paths are then persisted, so later passes do not re-expand the wildcard. Each request item may be a complete Show Name, an Artist, Artist plus a calendar year (yyyy), Artist plus an exact yyyy-mm-dd date, or Artist plus a yyyy-yyyy/yy-yy range. Artist matching checks Artist DB masters and aliases. Artist plus yyyy selects that entire calendar year. A yy-yy range moves forward across a century when needed, so 99-01 means 1999-2001. A rooted filesystem path, visible volume label, [Volume], or [Volume] path may also be used. Rooted paths and bracketed volume forms are copied directly to the Destination. A bare volume label is direct only when it does not also match an Artist/alias or exact Show; if it collides, Preview reports it as ambiguous and [Volume] is required for the whole-volume copy. TLO tracks any inventoried Shows inside the copied tree so other request items do not copy them again.

Q: Are there Copy Request source/Destination or whole-volume safety rules?
A: Yes. Destination must be separate from the source: TLO rejects Destination equal to the source, inside the source, or an ancestor that already contains the source. Source-as-target is never counted as Already Satisfied or Complete. TLO reserves the final name, copies into a TLO-owned .tlo-copy-* temporary sibling, verifies it, and only then publishes the final folder. A failed reservation never authorizes deletion of the pre-existing Destination folder, and stale temporary cleanup removes only folders carrying TLO's ownership marker. For whole-volume copies, TLO excludes operating-system-managed root folders that should not be copied: Windows System Volume Information and $RECYCLE.BIN; macOS .Spotlight-V100, .fseventsd, .Trashes, and .TemporaryItems. These exclusions also apply when the volume root is written as a direct path. Preview/reporting identifies the exclusions, and the same set is used for size calculation, copy, and verification.

Q: What happens if all of the source drives are not connected for a Copy Request?
A: TLO copies only matching Shows that have an inventoried source on a currently connected volume. Shows known to the inventory but located only on disconnected volumes remain Waiting For Volumes, not failed. Continue the same request after connecting more drives. Preview also lists which remaining volume labels would satisfy the most outstanding Shows.

Q: Can I have more than one Copy Request?
A: Yes. Different Path(s) expressions are independent persistent requests, and the same Path(s) expression sent to a different Destination is also independent. Any .txt inputs are expanded into the saved request when it is created; later Continue passes use that persisted aggregate rather than rereading the source files. Process All Active Requests processes every request that is not Closed, with a separate free-space preflight for each Destination.

Q: How is a Copy Request completed or stopped?
A: TLO reports Complete when every currently matched Show is satisfied and there are no unmatched request items. Broad Artist/range requests are re-evaluated later and can become active again if new inventory adds matching Shows. If you are done even though unmatched items remain, use Close Request; its terminal state is Closed. Delete Request removes only TLO's request state/history and never deletes copied music.

Q: How can Copy Requests use my backup drives without inventorying every backup?
A: Open the upper-right hamburger menu and choose Redundancy Groups. Enter one equivalent-volume group per line, for example Juke3 = Back-up3 = Back-up3a. The order is the precedence: Juke3 is tried first, then Back-up3, then Back-up3a. You may enter visible volume labels or currently accessible volume/root paths; paths with spaces do not require quotes. TLO stores the resolved volume labels and Copy Requests uses the same inventoried rootless path on whichever equivalent member is connected. Only one copy needs to be inventoried.

Q: What does Close do in Redundancy Groups?
A: Close dismisses the Redundancy Groups window without saving unsaved editor changes. Use Save to store changes.

Q: What support email is shown in Help > About?
A: Help > About lists support@traderslittleorganizer.com as the TLO contact email.

Q: How safe is deleteReplacedFolders.bat/deleteBackupFolders.sh?
A: Add Shows writes only targets that remain at least one folder below a recognized drive/mount root. Literal .. traversal, bare roots such as E:\\ or /mnt/e, drive-relative E:, TLOHome, and ancestors of TLOHome are rejected. If an older cleanup script already exists when Add Shows starts, Continue archives it under TLOHome/logs and starts a fresh script. On Windows, deleteReplacedFolders.bat records every source as [Volume Label] (or [] when unlabeled) followed by a fully quoted path. The label identifies the volume where the path was found; it does not have to be connected during generation. At execution, each labeled Windows entry verifies the live drive label before any rmdir: a mismatch, a disconnected drive, an unavailable probe, or an empty live label means SKIPPED instead of deleted. [] entries are non-destructive, with only a commented-out example rmdir. To change a drive letter, edit the single TLO_DELETE_TARGET assignment for that entry; its volume probe and rmdir share that target. The expected label is encoded in the generated script. To target a different labeled volume (such as another backup with a different name), regenerate an entry for that volume rather than simply changing a path or comment. Review all targets before running the batch. Windows scripts also switch cmd.exe to UTF-8 code page 65001.

Q: How does TLO know an automatic update was authorized by the TLO release owner?
A: TLO requires TLO_UPDATE_METADATA.json plus TLO_UPDATE_METADATA.sig for every genuinely newer release. The pinned RSA public key must be at least 3072 bits, and the signed release_tag must exactly match the candidate GitHub release tag. The selected ZIP must match the signed name, size, SHA-256, build, package type, and platform/layout. GitHub's own asset digest is discovery information rather than the trust anchor.

Q: Why doesn't an older unsigned GitHub release cause an update-signing error?
A: TLO compares the recognizable GitHub release build number with the installed build before asking for signed update metadata. An older or equal release cannot be installed as an update, so it is simply reported as not newer. Any release with a higher build number still must pass the independent signature check before TLO accepts or downloads it.

Q: Where is the update-signing private key stored?
A: Only on the trusted Windows release computer. New-TLOUpdateSigningKey.ps1 stores it in a Windows-DPAPI-protected file for the current user. It must not be committed, uploaded to GitHub, or copied into release assets. Keep an offline backup of the key files and the Windows profile/recovery material needed to use the DPAPI-protected private key.

Q: Does tlo-search have a default TLOHome if I do not set one?
A: No. Supply --TLOHome (or the retained hidden compatibility alias) or set the TLOHome environment variable; otherwise Search stops with a clear TLOHome-required error.

Q: Why might tlo-main or tlo-search ask for macOS permissions again after an update?
A: The macOS GUI bundles are named tlo-main.app and tlo-search.app. macOS can treat renamed/replaced application bundles as new applications, so previously granted Files and Folders, removable-volume, or Full Disk Access permissions may need to be granted again after an update. This does not indicate that TLO changed the underlying collection files.

Q: What happens if the Recycle Bin is unavailable during corruption handling?
A: On native Windows, TLO first verifies that the volume is fixed local NTFS, that the per-volume Recycle Bin settings permit recycling, and that the selected item fits the reported capacity. If the Recycle Bin, policy, quota or filesystem cannot be confirmed, TLO retains the affected content, logs the failure, and does not attempt a permanent delete or additional removals for that show. Dry Run never moves content. Under WSL the gio command uses Linux/WSL Trash services (often a .Trash-UID directory on the mounted drive), not necessarily the Windows Recycle Bin; failures leave content in place. Native Windows behavior on removable drives and with recycling disabled still requires actual Windows testing.


Q: Does TLO search PATH for PowerShell on Windows when grouping physical drives?
A: No. On native Windows TLO derives System32\WindowsPowerShell\v1.0\powershell.exe from the Windows directory provided by the operating system API and uses only that path. If it cannot identify or run the trusted helper, it leaves the physical disk identity unknown and uses the existing volume-grouping fallback. Under WSL, Windows interop executables follow the separate Linux PATH lookup policy.

Q: What happens if Tag Copy is cancelled or interrupted before copying finishes?
A: TLO copies into a temporary .tlo-partial-* folder beside the destination, verifies the complete relative folder/file structure and file sizes, then atomically publishes it under the final show name. An interrupted worker or power loss can leave that temporary folder, but it is excluded from inventory and is not a complete copied show. TLO does not overwrite an existing destination or delete the Tag Copy source. Copy/Delete Original transfer staging is handled separately.

Q: What happens when Copy/Delete Original is interrupted or fails during staging?
A: Cross-filesystem Copy/Delete keeps the source intact while it copies into a .tlo-partial-* sibling, verifies all relative files, folders, sizes and SHA-256 contents, and atomically publishes the completed show. Only then does it remove the original. Same-filesystem Copy/Delete moves the entire source directory atomically into a .tlo-partial-* staging name and then into the published name without copying or hashing; a normal publication error attempts atomic restoration of the original source name. Worker death may leave a complete staged same-filesystem show or an incomplete staged cross-filesystem copy, both excluded from inventory. Do not delete a staged tree without examining the exact source/destination state. Source-cleanup errors after publication preserve the verified destination and require reconciliation.

Q: Has anything changed about opening files through the Inventory Update window?
A: No visible command was removed. The unused Inventory Update path-opening helper was retired. Current Main GUI open-path actions continue through a single hardened opener that rejects network/device paths and symbolic links. On Windows, selecting a file in Explorer does not execute its associated application.

Q: Why does TLO include FFmpeg source and a license?
A: FFmpeg is a separate LGPL-licensed audio-processing tool. Approved native TLO packages include its corresponding verified source, build recipe, and LGPL notice under THIRD_PARTY/FFmpeg. It is used for SHN conversion and audio stream checks.
