Q: Is TLO a commercial application?
A: No. TLO is freeware.

Q: What does TLO do well?
A: TLO inventories live-music collections, identifies show metadata, creates searchable inventory output, and can tag supported audio files. Results depend on folder names, setlists, tags, database coverage, and optional online lookup sources.

Q: Does TLO inventory absolutely every music file?
A: Yes. TLO continues checking nested folders after it finds music in a parent show folder so a nested opening act can be discovered as a separate show. Ordinary CD/Disc/Set wrapper folders continue through the normal grouping rules.

Q: Do I need to define TLOHome before I start?
A: Yes. TLOHome is the root for the applications, databases, logs, setlists, and inventory output. Set it with the TLOHome environment variable or the documented --TLOHome command-line option. The Inventory and Search GUIs resolve it at startup and display it as a read-only label.

Q: What else is required before the first run?
A: A complete installation must contain TLOHome/TLO_DBs/artists.sqlite and TLOHome/TLO_DBs/venues.txt. Full Inventory also requires Search Path. Path(s) can contain one or more semicolon-separated direct roots using the same line grammar as toBeInventoried.txt, or the fully qualified path to any .txt control file using that format. TLOHome/toBeInventoried.txt is not read automatically. Optional settings include TLOCurrentStorage for Add Shows, SETLISTFM_API_KEY for setlist.fm lookup, and SETLISTFMUPGRADE_API_KEY to enable setlist.fm upgrade. SETLISTFMUPGRADE_API_KEY should contain the same API key value as SETLISTFM_API_KEY.

Q: Is toBeInventoried.txt still used automatically?
A: No. Build 461 keeps toBeInventoried.txt only as an example/template in COMPLETE installations. To use that format, explicitly put the full path to toBeInventoried.txt (or any other .txt control file) in Search Path.

Q: Can Search Path contain more than one root?
A: Yes. Separate direct Path(s) entries with semicolons. Each direct entry may use the same optional [Volume], --$slam, --$copy, and --$copy-delete directives as a control-file line. A .txt Search Path entry is expanded using the same line/comment rules as the former toBeInventoried.txt input file.

Q: Can I drag more than one folder into the Path(s) box?
A: Yes, on native Windows. Build 463 corrects the Windows TkDND handling so every folder or .txt control file selected in one drag is retained, and each later drag appends to the existing Path(s) value instead of replacing it. Items are separated automatically with semicolons. For example, dragging A, then B, then C and D together produces A;B;C;D. Commas are ordinary path characters, so a dropped folder such as Van Morrison 1994-12-03 Dublin, Ireland needs no special quoting.

Q: How difficult is it to set the TLO-related environment variables?
A: The Windows and macOS/Linux/WSL setup steps are described in Sections 4 through 6 of the User Manual.

Q: Can TLO change or remove original material?
A: Yes. Rename Compliantly, Tag in Place, SHN-to-FLAC conversion, and Tag Copy/Delete Original can change or remove original files or folders. Same-partition Copy/Delete Original transfers are directory moves and do not use file-size comparison. Cross-partition Copy/Delete Original transfers recursively copy the complete identified folder tree and verify relative file paths, file sizes, and descendant folder structure before the source is removed. Tag Copy also copies the complete folder tree and verifies the same file and folder structure because it always creates and retains a separate copy. SHN conversion is also verified before removing the source. Build 456 provides the standalone tlo-reverse CLI for logged folder operations. It can reverse Rename Compliantly by itself, Tag Copy/Delete Original with or without compliant renaming, and Tag Copy. The operation type is inferred from the success log; audio tags are never restored or changed. Ambiguous or conflicting folder states are left untouched. Keep an independent backup when preserving pristine source material matters.

Q: What should I do if Inventory says an interrupted sibling-collection move requires recovery?
A: Build 465 normally recovers the journaled move automatically before scanning and then continues Inventory. This includes the case where the recovery container has the same pathname as one of the original collection members and the case where the journal was written with native-Windows paths (for example E:\boots\...) but recovery is running under WSL (/mnt/e/boots/...), or vice versa. TLO translates those equivalent path forms before applying the same strict parent/member validation. If automatic recovery cannot proceed, TLO prints the recovery container, journal, planned final folder, every original/staged member path with its current state, and the original journal path form when it differs. Close programs that may have those folders open and run a normal (non-Dry-Run) Inventory again. Do not delete the .tlo-sibling-consolidation.json journal or manually merge/delete the recovery folder; BOTH or MISSING states require review of the exact paths TLO reports. Dry Run never moves folders and will tell you to run a normal Inventory for recovery.

Q: What happens when an alternate collection already has an unsuffixed folder with the same name as the collection?
A: Build 466 no longer creates a nested Name\Name folder. TLO builds the aggregate in a new temporary sibling directory, moves the unsuffixed original member into it as Name (alt0), then moves alt1, alt2, and later accepted alternatives alongside it before finalizing the aggregate under the normal shared collection name. alt0 remains first for continuous collection-wide track numbering. If the transaction fails or is interrupted, the journal records both the original and staged names so rollback restores the exact original unsuffixed folder. Older Build 464/465 recovery journals remain supported.

Q: What happens if I inventory the same drive again?
A: For a named volume, TLO deterministically replaces, prunes, or appends the affected scope according to whether the new path is the same as, a parent of, a child of, or separate from the stored paths. It does not ask a Skip/Re-inventory question. Blank-volume runs append to the shared blank-volume logs and can create duplicate inventory entries if the same content is scanned again.

Q: Can Rename Compliantly rename my entire collection or search root?
A: No. TLO may aggregate true CD, disc, part, or volume siblings only when every direct music-bearing child under the parent belongs to that one release relationship. If any direct music-bearing sibling is unrelated, the folders remain separate and the broad collection/search parent is never renamed as one show. Text such as v.2 inside a larger descriptive parenthetical does not count as a volume suffix.

Q: Does Artist in Album Tag apply during Full Inventory?
A: Yes. When checked, Full Inventory and GUI Tag with Tag in Place, Tag Copy, or Tag Copy/Delete Original write Album as Artist followed by the resolved date, venue, location, and preserved parentheticals. Add Shows tagging and standalone tlo-tag use the same album rule.

Q: Can I see what TLO plans to do before it changes anything?
A: Yes. Full Inventory, Add Shows, and Tag show Review Operation before starting. Every Review Operation dialog reports all main-window checkbox values in the same order. Tag has no duplicated option checkboxes. GUI Tag now runs directly from the main Inventory window using the master Path(s), including any inline --$slam directives, the tag-mode choice, and all current main-window options; it no longer opens a separate Tag window. Add Shows retains only its action-specific controls. Dry run is controlled only by the checkbox on the main Inventory window. With Dry run selected, click Inventory, Tag, Process New Shows, or Process Potential Duplicate/Upgrades. Dry run resolves and displays resulting show names and planned actions. When tagging applies, it lists each applicable audio file with the Artist, Album, Track, and Title values that would be written, plus the title source, planned SHN-to-FLAC target, potential duplicate matches, or reason a file would be skipped. Dry run does not write tags, convert, rename, copy, move, delete, create inventory output, or change TLO logs.

Q: Are trailing folder parentheticals preserved in the resulting show name?
A: Yes. TLO captures trailing parenthetical items before it cleans the folder name for metadata parsing, then restores them after artist, date, venue, and location normalization. For example, Danny Gatton 1994-03-13 Bottom Line NYC (set 2) resolves to Danny Gatton 1994-03-13 Bottom Line New York, NY (set 2). Multiple trailing parentheticals remain in source order without duplicate entries.

Q: How does Check for updates choose a package if a release has only updates or only complete installs?
A: TLO uses only the exact package for the installed operating system and package layout. It prefers that platform/layout's update ZIP. If the release has no matching update ZIP, it may download the exact matching complete ZIP instead. It never substitutes the source bundle, a generic ZIP, another operating system, or the other Windows onefile/onedir layout. After the SHA-256 check, TLO also validates the package manifest before reporting a successful download.

Q: What does Auto update do when it finds a newer build?
A: Auto update now asks before downloading. The prompt has Yes and Skip buttons. Yes downloads the verified exact-match ZIP to your Downloads folder and returns; TLO does not install or extract it. Skip closes the prompt and downloads nothing. The automatic check is still limited to at most once per day, so Skip does not cause another prompt on every startup during that interval. Manual Check for updates keeps its direct-download behavior.

Q: Can an update ZIP include the TLO databases?
A: Yes, when the release was explicitly built as a database-refresh update. Normal update ZIPs still omit TLO_DBs. A database-refresh update contains exactly TLO_DBs/artists.sqlite and TLO_DBs/venues.txt and omits your inventory, setlists, logs, staged folders, and other user-created output. Check for updates reads the package manifest and ZIP contents and tells you whether the downloaded update includes those databases; applying such an update replaces those two master database files.

Q: Does TLO recognize same-month multi-day dates such as 1970-04-12-13?
A: Yes. TLO accepts a first yyyy-mm-dd followed by one or two strictly ascending day values, using dashes or commas, for example 1970-04-12-13, 1970-04-12-13-14, 1970-04-12,13, and 1970-04-12,13,14. Textual equivalents such as 12-13 April 1970, April 12-13, 1970, and 1970 April 12-13 are also accepted. Every day must be valid for that month and year. The first day becomes the canonical TLO Date, while the complete original multi-day range is retained in PARENTHETICALS. A descending, repeated, or impossible range is rejected as a whole. Existing year-range rules are unchanged.

Q: Can TLO handle a folder such as RTF Paris 7 March 76 flac16?
A: Yes, beginning with Build 460, but only through a guarded non-compliant fallback. The artist prefix itself must resolve uniquely in artists.sqlite; TLO does not manufacture initials, so RTF must already be an alias/artist term in the database. The date uses the normal TLO date parser, and everything after the date must be recognized technical media/source text such as flac16, flac24, shn, wav, 16-bit, 24-bit, SBD, AUD, FM, matrix, soundboard, or audience. Strong state/country-anchored place text and exact venues.txt matches are used normally. A single unanchored word such as Paris is only retained if eTreeDB, selected setlist metadata, and setlist.fm do not provide stronger venue/location information. Unknown multi-word text is not promoted to a location.

Q: Can Compliant and Rename Compliantly be selected together?
A: No. They are mutually exclusive. In the main Inventory window, checking either one automatically unchecks the other. Tag and Add Shows inherit the resulting main-window values. On the inventory, GUI-launcher, and standalone-tagger command lines, using --compliant and --rename-compliantly together produces an argument error.

Q: When does TLO ask for a Tag Copy destination?
A: Checking Tag Copy or Tag Copy/Delete Original only selects the mode. TLO asks for the destination after Inventory or the main-window Tag action is started, including when Dry run is selected. Both dialogs validate the full path and show available storage. Tag Copy copies the complete identified folder tree and verifies relative file paths, sizes, and descendant folder structure while retaining the source. The copy/delete dialog additionally warns that originals will be removed; same-partition transfers move the complete folder tree with no size totaling or comparison, while cross-partition transfers recursively copy and verify the complete tree before deletion.

Q: How do I reverse a combined Tag Copy/Delete Original and Rename Compliantly run?
A: Run tlo-reverse with one fully qualified folder or containing path, for example tlo-reverse "D:\Music\moved show". TLO reads successful folder mappings from TLOHome/logs/tags*.txt and compatible tag*.log files and infers whether the logged action was Rename Compliantly, Tag Copy, or Tag Copy/Delete Original. No operation-type flag is normally required. Copy/Delete restores the exact logged destination to the exact original path, whether or not compliant renaming was enabled. Rename-only renames the folder back. Tag Copy leaves the original and removes only the exact logged copy after a file-set safety check. If more than one run is applicable, use a narrower path or --log; use --dry-run to preview. Audio tags are never changed. Results are appended to TLOHome/logs/reverseFolders.log.

Q: When does TLO call a same-named show a copy instead of an alternate?
A: A matching Show or compliant folder name is not enough. Before TLO uses a (copyN) qualifier or folder suffix, it compares the complete recursive trees. The relative folders (including empty folders), relative files, file sizes, and every file's byte contents must all match. TLO uses SHA-256 content comparison after the faster structure and size checks. If anything differs, or a comparison cannot be completed, TLO uses (altN) instead. File timestamps do not matter. A source folder that already carries (copyN) is also rechecked before that qualifier is used in the Show name.

Q: Where are the settings for each run recorded?
A: After you choose Start in Review Operation, TLO appends the action, local date/time, and the same reviewed settings lines to TLOHome/logs/runSettings.log. The file is shared by Full Inventory, Tag, Process New Shows, and Process Potential Duplicate/Upgrades, including Dry runs. Command-line Inventory and Tag use the same log. Choosing Go Back or closing Review Operation does not create an entry.

Q: Where do I find problems after a run?
A: The completion summary includes View Issues and Open Logs. View Issues groups consequential problems by reason, such as unidentified shows, missing setlists, track-title mismatches, unreadable audio, copy or verification problems, online lookup problems, and other tagging or file errors. Successful parser decisions such as selecting the correct contiguous numbered song block are informational and no longer appear as tagging warnings. Normal creation/update status for unidentifiedShows.txt, including a result of zero unidentified shows, is also informational and does not appear as a warning. The Issues window horizontal scrollbar now scrolls long Explanation and Path columns. Select an issue and use Open Path when TLO has a usable path for it.

Q: How can I donate to TLO?
A: Open the upper-right hamburger menu in the Inventory window and choose Donate. Donate > Venmo shows @James-Scarano-3. Donate > Check shows James Scarano, 49 Majestic Ave., Nashua, NH 03063. The donation details use normal dark menu text rather than disabled gray text.

Q: Why does the Current Operation activity indicator move slowly?
A: The indeterminate activity indicator moves at one-tenth of its former speed in Inventory, Tag, and Add Shows. This is only a visual animation change; it does not slow inventory, tagging, Add Shows, elapsed-time updates, or worker processing.

Q: Where does TLO store setlist.fm rate-limit information?
A: Build 356 and later store it under TLOHome/logs/setlistfm-state. TLO no longer uses a shared system temporary-directory state file. A worker abandons a blocked reservation after 20 seconds and continues without that lookup.

Q: How do I safely remove duplicate folders?
A: Use tlo-deleteDupes with a fully qualified search path. TLO discovers candidate siblings from exact X/(copyN) families and from matching normalized artist/date names, then compares copies with one another as well as with unsuffixed folders. Folders with the same complete recursive structure, relative file names, and file sizes form a content-equivalence cluster. TLO keeps one folder per identical cluster, preferring an unsuffixed name; if the cluster contains only numbered copies, it keeps the lowest-numbered copy. The other identical cluster members are moved as whole folders into a folder named duplicates at the root of the partition containing the search path. Thus, if X differs from X (copy2) and X (copy3), but copy2 and copy3 match each other, TLO keeps X and copy2 and moves copy3. TLO creates the duplicates folder if needed, never overwrites an existing holding-folder entry, and appends each moved folder's original full path to TLOHome/deletedDirs.txt. When candidate folders differ, TLO records short CSV lines in TLOHome/deleteDupesMismatches.txt using folder name, folder name, and a simple reason such as different number of files, different sub-structure, or 01.flac different sizes.

Q: How can I research what TLO found in the comp and meta logs?
A: In the main Inventory window, click Research and enter an artist followed by a date, a venue, or a date. Research accepts every date form recognized by TLO Inventory, including partial/unknown forms such as xxxx-xx-xx, 19xx-xx-xx, 20xx-xx-xx, and 202x-xx-xx, textual-month dates, compact dates, slash dates, supported year ranges, and same-month multi-day ranges such as 1970-04-12-13 or 12-13 April 1970; a standalone four-digit 19xx/20xx year is also accepted. Multi-day ranges match using their canonical first day. TLO normalizes the date for matching and returns every matching metadata record plus all correlated comp-log paths. It then continues through every meta*.log and comp*.log line and adds an ALL RELATED RAW LOG LINES section with every directly related occurrence and its log filename/line number; it does not stop at the first occurrence. The standalone tlo-research app performs the same search and writes the same complete result to the console.

Q: Does TLO accept 19xx-xx-xx and 20xx-xx-xx as dates?
A: Yes. They are legitimate century-known partial dates. TLO requires the less-significant components to remain unknown, so 19xx-xx-xx and 20xx-xx-xx are valid, while forms such as 19xx-05-xx, 20xx-xx-14, 1xxx-xx-xx, and 2xxx-xx-xx are not.

Q: What does (pdupNN) mean in Add Shows?
A: Beginning with Build 399, when Process New Shows has Check for Duplicates selected and every matching bootlist entry is on another storage partition, TLO assumes those existing folders are unavailable for comparison and keeps the incoming show with a potential-duplicate marker such as (pdup01), (pdup02), and so on. This is not a copy/alternate determination. If a matching entry is on the current partition, or TLO cannot determine the partition, the existing duplicate review and copy/alternate checks remain in effect. Rename Compliantly applies the pdup marker to the physical folder name; otherwise the folder name is left as supplied.

Q: Does standalone tlo-tag use the same setlist.fm, Thorough Setlist Matching, and corruption controls as Inventory?
A: Yes. tlo-tag.py/tlo-tag.exe accepts the same lookup, Thorough Setlist Matching, corruption, and Delete extra tags controls. setlist.fm still requires eTreeDB. GUI Tag uses the current main-window values directly and no longer opens a separate Tag window. Corruption is checked before tag mutation using the same fail-closed rules as Inventory.

Q: Can TLO tag MP3 files and handle corrupt MP3 files like FLAC?
A: Yes. Build 467 treats MP3 as a first-class taggable format. MP3 files use the same Artist, Album, Track Number, and Title assignment flow as FLAC and participate in the same corruption population, percentage calculation, individual-file Keep/Delete policy, and folder Never/100%/threshold policy. Unverifiable MP3 reads fail closed just like FLAC.

Q: What does Delete extra tags do?
A: Delete extra tags is a main-window checkbox that defaults off and is also available as --delete-extra-tags. When selected, TLO clears tag metadata on files it tags and keeps only Artist, Album, Track Number, and Track Title. Other metadata, including comments and embedded tag artwork where supported, is removed. When the checkbox is off, TLO preserves unrelated metadata under the established tagging rules.

Q: Does Tag still open a separate Tag window?
A: No. Build 469 removes the GUI Tag child window. Click Tag in the main Inventory window; TLO uses the master Path(s), including inline --$slam directives, the selected tag mode, lookup/corruption/tagging options, Dry run, Performance Mode, and Max Workers ceiling. Progress and console output remain in the main window. The standalone tlo-tag command-line application remains available.

Q: What happens to the corruption folder controls when Corrupt files is Keep and report?
A: Build 469 treats Keep and report as report-only corruption handling. Folder removal is effectively Never, and the Folder removal and Folder corruption threshold controls are greyed out. Select Delete corrupt files to re-enable folder-removal choices; the threshold value is enabled only for At threshold.

Q: Why are the setlist.fm checkboxes disabled?
A: If SETLISTFM_API_KEY is missing or blank when the Inventory GUI starts, both setlist.fm controls are unchecked and disabled. If SETLISTFM_API_KEY is present but SETLISTFMUPGRADE_API_KEY is missing or blank, normal setlist.fm remains available but setlist.fm upgrade is unchecked and greyed out. To enable upgrade, set SETLISTFMUPGRADE_API_KEY to the same API key value as SETLISTFM_API_KEY before starting TLO. TLO never displays either key.

Q: What does Max Workers mean?
A: Max Workers is a ceiling, not a request to create that many workers. The GUI initializes it to the machine CPU count unless a positive launcher value is supplied. Performance Mode and processing constraints decide how many workers a phase actually uses, and TLO may use fewer because paths share a physical drive, there are fewer parallel work groups, or a phase must serialize work for correctness.

Q: Will Rename Compliantly fix capitalization-only differences in a folder name?
A: Yes. Build 471 treats exact spelling and capitalization as part of the compliant folder name. If TLO resolves the canonical artist as Dave Van Ronk, a folder named dave van ronk 1978-02-17 Main Point Bryn Mawr, PA is renamed to Dave Van Ronk 1978-02-17 Main Point Bryn Mawr, PA. On case-insensitive filesystems TLO uses a temporary sibling rename when necessary so the exact capitalization is applied without treating the same folder as a collision or creating an alternate/copy suffix. Build 479 limits that capitalization correction to case-poor local text (for example kirjurinluoto / pori -> Kirjurinluoto / Pori) when the online value provides useful mixed case. Already good mixed-case text is not degraded to all caps, and a genuinely different online venue/location still does not override earlier path metadata. The rule applies to Full Inventory/GUI or standalone Tag and Add Shows.

Q: What does TLO do when a show or collection has xxxx-xx-xx and no venue or location?
A: Build 473 can add a separate non-geographic descriptor instead of inventing a venue or location. It looks conservatively at the setlist header before the track list for explicit Collection, Release, Session, Broadcast, Program, Recording, and similar labels; strong session/broadcast/collection text; quoted or decorated release titles; then a descriptive setlist filename; and finally meaningful folder-name residue after removing artist/date, disc/set/part, and technical-format tokens. Song rows, source/lineage text, generic housekeeping names, and prose are rejected. For example, a collection may become Pink Floyd xxxx-xx-xx Early Flights. The metadata log records DESCRIPTOR and DESCRIPTOR_SOURCE, while Venue and Location remain blank. If no safe descriptor is found, TLO keeps the normal Artist xxxx-xx-xx name.

Q: What syntax does the main Path(s) box use now?
A: Build 476 uses the same grammar as one toBeInventoried.txt data line, with multiple Path(s) entries separated by semicolons. A direct entry can be a path by itself or include [Volume], --$slam, --$copy, or --$copy-delete. Commas and apostrophes/single quotes are ordinary path/directive characters and do not require quotes. Matching double quotes remain accepted as optional explicit quoting. Build 479 automatically double-quotes a dragged path only when the folder name itself contains a literal semicolon, so that legal semicolon remains inside one Path(s) entry. Examples: C:\Boots\Grateful Dead ; C:\Boots\Pink Floyd --$slam Pink Floyd ; C:\Boots\Van Morrison 1994-12-03 Dublin, Ireland;D:\Incoming --$copy E:\TLOCopies. You can also enter the full path to any .txt control file that uses the normal toBeInventoried.txt line/comment rules.

Q: Where did the main Slam box go?
A: Build 474 removes the separate Slam (optional) GUI field. Put an artist override beside the applicable Path(s) entry instead, for example C:\Incoming\RTF Paris --$slam Return to Forever. The inventory CLI --$slam option remains available for command-line use.

Q: What does Manual Tweaks do?
A: Manual Tweaks opens Manual Updates for user-directed folder/inventory corrections. Original accepts one folder or one .txt file. For a folder, enter the desired leaf folder name in New Name or drop one folder onto New Name; TLO keeps only its leaf name, and the drop does not depend on Original already containing a valid folder. Update Tags is checked by default. When it is checked, Save updates the tags in the corrected folder before finalizing the replacement setlist/bootlist inventory identity; uncheck it when you want the manual inventory correction without changing tags. TLO renames in place when needed, removes the old bootlist/setlist identity, and adds the new identity while preserving the old bootlist parent/volume path. If the folder was already renamed to the requested name in that same parent, Save can still repair the inventory. For a .txt Original, New Name is disabled and every non-comment line must be Path ----> Folder Name; blank lines, # comments, and REM comments are ignored. The one Update Tags choice applies to every line in that Save.

Q: Did Add Shows change in Build 474?
A: No. Only the visible main-GUI button label changed from Add Shows (incremental) to Add New Shows on two lines. The existing Add Shows/Updater functionality is unchanged.


Q: What happens in Manual Updates if Original is not in bootlist.csv but is still in unidentifiedShows.txt?
A: Beginning with v1.7 Build 475, TLO checks unidentifiedShows.txt by exact Original path first and then by a unique matching leaf folder name. If it finds the unresolved show, it opens "Where is the unidentified show going?" and asks only for the destination Path. TLO does not move or rename anything in this branch; the physical change is assumed to have already been done manually. Enter or drop either the destination parent folder or the already-renamed New Name folder itself. If the supplied Path already ends in New Name, TLO strips that leaf to get the parent; otherwise it uses the supplied Path as the parent. If Update Tags is checked (the default), TLO updates the tags in that already manually changed folder before finalizing the inventory update; if unchecked, it leaves its tags alone. Build 479 makes a parseable New Name authoritative for the corrected Artist/Album tag identity and disables SHN conversion inside Manual Updates, so SHN originals are not removed by this repair workflow. TLO then inventories parent\New Name, removes the resolved line from unidentifiedShows.txt, writes canonical [Volume] rootless-path inventory data, and exports the replacement setlist. A .txt Manual Updates batch uses the same rule and collects all required destination prompts before applying the batch.

Q: Do commas or apostrophes in Path(s) require quotes?
A: No. Semicolons are the Path(s) entry separator. Commas and apostrophes/single quotes are ordinary characters inside paths and directive values. Build 478 therefore accepts names such as Tito Puente's without treating the apostrophe as the start of a quoted value or reporting an unmatched quote. Matching double quotes remain accepted as optional explicit quoting. Build 479 automatically double-quotes a dragged path only when the folder name itself contains a literal semicolon, so that legal semicolon remains inside one Path(s) entry.

Q: Can MP3 tags help identify a show during Inventory?
A: Yes, beginning with Build 480 in non-compliant mode. TLO samples metadata from up to two supported FLAC or MP3 files and can use ALBUMARTIST, ARTIST, ALBUM, and DATE as low-priority identification evidence. Artist evidence still follows the normal precedence: inline --$slam and stronger path/setlist evidence come first; a DB-matched sampled tag artist is used only after those stronger sources fail, and an unmatched raw tag artist is the final fallback. Compliant mode does not read or use FLAC or MP3 metadata tags.

Q: Does tlo-ggi accept --tag-path?
A: No. Build 480 removes the dead GUI-launcher --tag-path option because GUI Tag uses the required main Path(s) field, including inline --$slam directives. --tag-path and positional tagPath remain supported by the standalone tlo-tag command only.

Q: When can setlist.fm run if eTreeDB already found the show?
A: In normal mode, setlist.fm remains a fallback when eTreeDB did not return usable venue/location data. Thorough Setlist Matching is the explicit exception: when Thorough and setlist.fm are enabled, TLO may query setlist.fm proactively for corroboration/deconfliction even after eTreeDB returned usable data. Thorough collection does not give setlist.fm extra overwrite authority.

Q: What security hardening was added in Build 481?
A: Build 481 treats collection metadata and recovery state as untrusted input. TLO encodes control characters before writing machine-parsed logs, rejects malformed duplicate identity keys, bounds full setlist reads, refuses symlinked Tag Copy trees and symlinked sibling setlists, secures SHN temporary output, protects bootlist.csv from spreadsheet-formula interpretation, and prevents Issues actions from opening network/device paths or launching arbitrary files. Normal well-formed collections continue to use the same inventory/tagging behavior.

Q: Why can an interrupted sibling-collection recovery now stop instead of recovering automatically?
A: Automatic recovery now requires the recovery journal to match a nonce registry entry written by the same TLOHome under TLOHome/logs/sibling-recovery. This prevents a traded collection from planting a fake journal that tells TLO to move or delete unrelated files. A journal that is missing, oversized, malformed, or not registered stops Inventory without mutating the recovery container. Preserve the reported recovery container and journal for review rather than deleting them manually.

Q: Why can Tag Copy refuse a folder containing symbolic links?
A: Build 481 refuses Tag Copy when the source tree contains symbolic links so TLO cannot accidentally copy the contents of a link target outside the traded collection. Sibling setlist aggregation likewise ignores symlinked setlist files. Replace or remove the links deliberately before using those workflows.

Q: What does Copy Requests do?
A: Open the upper-right hamburger menu in the Inventory window and choose Copy Requests. Copy Requests copies a requested subset of the inventory to a Destination across multiple sessions and changing sets of connected source drives. A request stays saved under TLOHome/copyRequests, so you can copy what is available now, swap drives later, choose Continue, and TLO skips Shows already completed for that request.

Q: What can I put in a Copy Request .txt file?
A: Use the same blank-line, #, and REM whole-line comment convention as toBeInventoried.txt. Each data line may be a complete Show Name, an Artist, Artist plus a calendar year (yyyy), Artist plus an exact yyyy-mm-dd date, or Artist plus a yyyy-yyyy/yy-yy range. Artist matching checks Artist DB masters and aliases. Artist plus yyyy selects that entire calendar year. A yy-yy range moves forward across a century when needed, so 99-01 means 1999-2001.

Q: What happens if all of the source drives are not connected for a Copy Request?
A: TLO copies only matching Shows that have an inventoried source on a currently connected volume. Shows known to the inventory but located only on disconnected volumes remain Waiting For Volumes, not failed. Continue the same request after connecting more drives. Preview also lists which remaining volume labels would satisfy the most outstanding Shows.

Q: Can I have more than one Copy Request?
A: Yes. Different request files are independent persistent requests, and the same request file sent to a different Destination is also independent. Process All Active Requests processes every request that is not Closed, with a separate free-space preflight for each Destination.

Q: How is a Copy Request completed or stopped?
A: TLO reports Complete when every currently matched Show is satisfied and there are no unmatched request items. Broad Artist/range requests are re-evaluated later and can become active again if new inventory adds matching Shows. If you are done even though unmatched items remain, use Close Request; its terminal state is Closed. Delete Request removes only TLO's request state/history and never deletes copied music.

Q: How can Copy Requests use my backup drives without inventorying every backup?
A: Open the upper-right hamburger menu and choose Redundancy Groups. Enter one equivalent-volume group per line, for example Juke3 = Back-up3 = Back-up3a. The order is the precedence: Juke3 is tried first, then Back-up3, then Back-up3a. You may enter visible volume labels or currently accessible volume/root paths; paths with spaces do not require quotes. TLO stores the resolved volume labels and Copy Requests uses the same inventoried rootless path on whichever equivalent member is connected. Only one copy needs to be inventoried.
